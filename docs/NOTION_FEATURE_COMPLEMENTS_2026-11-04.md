# 통학메이트 기능 목록 보완사항

작성일: 2026-11-04  
비교 대상: [Notion 「대면 회의」(2026-11-03)](https://app.notion.com/p/uihyeonkim/40c5686b194380e6999be34754a27c6b?source=copy_link)  
구현 기준: PC022의 `C:\SSAFY\PleosShuttlePoC` 현재 코드와 저장된 검증 기록

> 노션은 0.1.6-poc 검증을 기준으로 작성되어, 이후 구현한 기관 서버·보호자 앱·Pleos ETA·자동 전송·알림 기능이 반영되지 않은 부분이 있다. 아래는 노션에 옮겨 적을 보완안이다. 이번 작업에서는 노션 본문이나 앱 코드를 수정하지 않았으며, 기존 코드와 시험 결과를 대조했다.

## 1. 먼저 바꿔야 할 설명

1. **“학부모 폰 기능은 모두 신규” → “하원 조회·진행 화면·알림·공유는 구현, 요청·승인 기능은 미구현”**
2. **“순정 내비에 구조화된 남은 시간·거리 필드가 없다” → “설치된 Pleos NaviHelper에서 목적지·경유지의 remainTime/remainDistance를 수신한다”**
3. **“보호자 화면에 도착 예정 시각 없음” → “내 아이 정류장과 대응하는 유효한 Pleos 남은 시간을 표시하고 갱신한다”**
4. **“일반 기록에도 주차브레이크 필수” → “일반 운행 조건과 문 제어 시험 조건을 분리한다”**
5. **“차량 앱의 서버 통신 가능 여부부터 검증” → “로컬 서버와 에뮬레이터·삼성폰 통신은 검증했으며, 외부망 운영은 별도 과제”**

“PoC 구현” 한 칸만으로는 실제 검증 범위가 드러나지 않는다. 앞으로 기능 상태와 검증 범위를 함께 적는 것을 권장한다.

| 표기 | 의미 |
|---|---|
| 구현 / 기기 확인 | 에뮬레이터 또는 삼성폰에서 해당 동작을 실제 확인한 기록이 있음. 실제 도로 주행 검증과는 다름 |
| 구현 / 자동 시험 | 코드와 합성 데이터 기반 단위·통합·UI 시험이 있음 |
| 구현 / 현장 미검증 | 구현은 있지만 실제 근접 상황·OEM 화면 정책 등 핵심 동작을 현장에서 확인하지 못함 |
| 부분 구현 | 해당 항목의 일부만 구현됨. 나머지를 함께 명시 |
| 미구현·별도 검토 | 현재 완료 기능으로 표시하면 안 됨 |

## 2. 노션에 독립 항목으로 추가할 기능

기존 문서의 넓은 “폰 연동” 또는 “정보 관리”에 포함될 수 있더라도, 아래 기능은 별도 행으로 적어야 현재 구현 범위가 드러난다.

| 추가 위치 | 기능명 | 노션에 넣을 설명 | 현재 확인 범위 |

## 3. 기존 기능 행의 수정안

### 3.1 차량 앱과 핵심 기능

| 노션의 현재 항목/설명 | 보완할 내용 | 권장 상태 |
|---|---|---|
| 핵심 3 / 정차 확인: 속도·기어·주차브레이크·UX가 모두 최신이고 브레이크 체결 | 일반 기록·출발·순서 적용은 최신 속도 0, P, SDK 출처/연결 및 차량 UX 조건을 확인한다. 주차브레이크는 문 제어 시험의 별도 조건이다. 실제 문 잠금 해제 안전 정책을 완화한 것은 아니다. | 구현 / 정책 시험. 기존 “브레이크 필수” 설명 수정 |
| 다음 목적지 안내 | Pleos 경로 요청을 연결하고, 현재 처리할 최대 3개 지점(경유지 최대 2개 + 목적지)을 대상으로 시간을 수신한다. 다음 구간으로 진행할 때 해당 순서에 맞게 다시 요청한다. | 구현 / 에뮬레이터 확인 |
| 남은 시간·거리: 연동 전, 추가 개발 | 목적지·경유지의 remainTime/remainDistance를 수신한다. 등록된 정류장과 일치하는 유효한 값만 보호자에게 보낸다. 수신 범위 밖의 뒤 순서 아이 시간은 임의로 합산하지 않는다. | 구현 / 실제 SDK 수신 + 자동 시험 |
| 안내 다시 재생: 추가 개발 | 현재 운행 단계/정류장 안내의 재생 기능은 구현되어 있다. 이것과 출발 전 안전띠·하차 전 도로 횡단 금지 등 별도 안전 안내 문구 묶음은 구분한다. | 재생은 구현, 안전 문구 체계는 별도 확인 |
| 기록 저장 실패·재시도: 추가 개발 | 로컬 저장 오류 시 기록을 보존하고 진행을 막는 처리, 기관 전송 실패 시 재전송 기능이 있다. 모든 저장 실패에 대한 별도 복구 UI까지 완성했다고 적지는 않는다. | 부분 구현 |
| 핵심 7 / 선생님·학부모 폰 연동: 신규 | 차량 → 서버 → 보호자 앱의 기록·진행·알림은 구현됐다. 선생님 전용 앱, 출결 사전 설정, 결석/변경 요청 승인·현장 기록 공동 편집은 별도 미구현이다. | 항목 분리 필요 |

### 3.2 학부모 폰

현재의 “9개 모두 신규, 기록 시각만 표시”라는 도입문부터 수정해야 한다.

| 기존 행 | 수정안 |
|---|---|
| 오늘 우리 아이: 기록된 승차·하차 시각 | 계정에 연결된 아이의 기록 조회와 오늘 하원 상태를 제공하는 구현 기능으로 변경. 자동 센서 판정이 아니라 차량 앱의 기록이라는 점 유지 |
| 진행 순번: 도착 예정 시각 없음 | 익명 중간 정류장 → 내 아이 하차 지점의 진행 화면, 버스 아이콘, 내 아이 Pleos ETA로 확장. 지도 없이도 현재 화면을 설명할 수 있도록 수정 |
| 하차·인계 알림: 신규 | 실제 구현된 알림을 출발(DEPARTED), 접근(APPROACHING), 도착(ARRIVED), 하차(ALIGHTED)로 구체화. “인계”가 독립 푸시 종류로 검증됐다고 적지 않음 |
| 받았어요 확인 | 미구현·선택 검토 상태 유지. 휴대폰 OS의 알림 수신과 사용자의 “받았어요” 확인은 다른 기능 |
| 결석·직접 데려감·하차 장소 변경 | 미구현 상태 유지. 기관의 명단/장소 관리와 보호자의 요청·승인 흐름은 다름 |
| 대리 수령인 등록·선택 | 미구현 상태 유지. 새로 만든 픽업 조회 링크 공유와 구분. 링크 수신자는 정식 수령인 승인 대상이 자동으로 되지 않음 |
| 선생님 확인 상태 돌려받기 | 요청 승인 기능은 미구현. 현재 운행 상태 갱신과 혼동하지 않도록 구분 |
| 지난 기록 보기 | 연결된 아이의 이벤트 조회와 오늘 완료 기록 보존은 구현. 날짜 검색·필터·장기 이력 화면까지 완료했다고 쓰지 말고 “부분 구현”으로 기재 |
| 번호 가림 연락 | 미구현 상태 유지 |

보호자 화면의 개인정보 설명도 “다른 아이 정류장은 전혀 보이지 않는다”에서 “앞선 정류장의 익명 순번·진행은 보이되, 다른 아이 이름·주소·좌표는 보이지 않는다”로 바꾸는 것이 정확하다.

## 4. ETA·알림·버스 표시를 설명할 때 지킬 기준

### Pleos에서 실제로 받는 것

현재 어댑터는 `getCurrentLocationInfo`, `getDestinationInfo`, `getWaypointInfo`를 호출하고 위치·목적지·경유지 콜백을 사용한다. 경유지가 있으면 `requestRouteWithWaypoints`를 사용한다. [C1]

- 내비가 반환한 남은 시간을 사용한다. 실제 모드에서 임의 정차 시간을 덧붙이거나, 시간 경과만으로 숫자를 계속 줄이지 않는다.
- 정류장 도착 후 새 구간 출발/경로 요청에 따라 받은 최신 값을 반영한다.
- 현재 구현이 검증하는 지점 묶음은 최대 3개다. 내 아이가 그 범위 밖이거나 일치 확인이 안 되면 ETA를 표시하지 않는다.
- 재탐색·목적지 변경·경로 불일치·오래된 관측은 기존 ETA를 무효화한다. 위치/시간 갱신이 약 30초 이상 끊기면 갱신 대기로 표시한다.
- 전송·조회는 약 5초 주기이며 네트워크 상태에 따라 지연될 수 있다. “실시간”을 지연 없는 즉시 동기화로 설명하지 않는다.
- 에뮬레이터의 일부 중간 경유지 좌표가 0으로 오거나 표시용 좌표가 없는 문제가 있었다. 이름·순서·전체 지점 묶음·최종 목적지 좌표가 모두 맞는 제한된 경우에만 등록한 하차 좌표를 대응시킨다. **시간은 Pleos 값이고 좌표는 등록값이라는 출처를 구분한다.** 좌표 API 자체를 고쳤다고 표현하면 안 된다.
- 전체 도로 경로선(polyline)을 확보한 것은 아니다. 보호자 폰의 버스 진행 표시는 실제 도로 위 GPS 추적선이 아니다.
- 현재 보호자 폰 기본 화면은 지도 없는 정류장 진행 UI다. 저장소에 남아 있는 과거 지도 관련 파일이나 공유 웹의 지도 옵션을 현재 보호자 폰의 핵심 화면으로 설명하지 않는다.

### 알림과 상태 변경

| 종류 | 발생 기준 | 해석 |
|---|---|---|
| 출발 | 연결된 아이의 운행 출발. 사용 가능한 해당 아이 ETA가 있으면 포함 | “하원을 시작했습니다”와 아이별 예상 시간 안내 |
| 접근 | 해당 아이의 최신·유효한 ETA가 0~2분이고 발송 조건 충족 | 도착에 대비하라는 안내. 하차/인계 기록 아님 |
| 도착 | 차량 앱에서 해당 아이 정류장의 도착을 확인하여 인계 단계로 진행 | 보호자에게 도착 상태 안내. GPS만으로 자동 확정하지 않음 |
| 하차 | 실제 차량 앱의 인계·하차 기록 | 보호자 완료 화면 및 하차 알림 |

발송 대기 중에도 연결·탑승·운행/경로·최신 상태를 재검사하고 오래된 알림을 취소한다. 접근·도착 FCM은 60초 TTL을 사용한다. 실제 FCM 전송 승인과 삼성폰 OS 알림 기록이 확인됐지만, 그것이 사용자가 읽었거나 아이를 인계받았다는 증거는 아니다. [E2, C4, C5]

차량의 근접·정차 안내는 별도 기능이다. 현재 정책은 차량과 지점의 거리 150m 이내, 해당 경유지의 내비 남은 거리 250m 이내, 최신 관측·목적지 일치·P/속도 0·UX 조건 및 3초 이상 유지 등을 확인한다. 임의 오버레이로 버튼을 항상 띄우는 기능이나 도착 즉시 앱을 강제로 전면 실행하는 기능으로 적지 않는다. [C2]

### 완료로 적으면 안 되는 부분

- 실제 도로 주행과 실제 어린이 승하차 현장 검증.
- 차량 근접 상황에서 OEM 알림 팝업 표시 및 탭 복귀의 현장 검증.
- 전체 정류장에 대한 무제한 ETA, Pleos와 같은 도로 경로선, 실제 GPS와 일치하는 보호자 버스 아이콘 위치.
- 공개 HTTPS 운영 서버, 외부 LTE에서 앱 없는 보호자가 링크를 여는 운영 검증.
- 강제 종료·OS 종료·부팅 뒤의 무조건 자동 전송 재개.
- 선생님 전용 앱, 결석/변경 요청 승인, 대리 수령인 승인, 보호자 “받았어요”.
- 안전한 보도 도착 확인의 별도 절차, 하차 확인 장치 연동, 센서 기반 어린이 식별/안전 판정.
- 운영용 이메일 소유권 검증·동의 관리·법정 제출 양식. 현행 초대의 이메일 일치 검사가 이메일 소유권 인증 전체를 대신하지는 않는다.

현재 실제 내비 시연에서 54/60/64분이 나온 것은 에뮬레이터 내비 위치가 판교이고 가상 하차 지점은 서울시청 부근이었기 때문이다. 하차 지점끼리 가까워도 첫 출발 위치가 멀면 짧아지지 않는다. 짧은 시연 시간을 원할 때 합성 시연 값을 실제 내비 응답이라고 소개하면 안 된다. [E2]
